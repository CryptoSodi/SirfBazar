### Completion update — 2026-09-29

Frontend handlers are now present for product bulk upload/removal, rider update/removal, staff update/status/removal, merchant document submission, unavailable-item/replacement suggestion, Socket.IO notifications and merchant support tickets. Settlement history was already connected. Authenticated localhost read checks passed for profile, settlements, products, riders, staff, support and notifications. The Socket.IO handshake was reachable.

Role boundaries remain enforced: `/payments/*` and `/orders/*` customer operations require `CUSTOMER`; rider delivery operations require `RIDER`; `/admin/*` refunds, coupon management, review/platform moderation and administration require admin roles. These are not valid merchant-dashboard integrations and were not connected with an admin or customer token. The public active-coupon catalogue is customer-storefront content, not a merchant management contract.

Device delivery: `/notifications/push-token` remains the Expo/mobile-token contract and is not used by this desktop React/Vite app. Desktop delivery now uses authenticated Socket.IO while open, browser Web Push through VAPID plus `/sw.js` when subscribed, and 15-second polling/focus as recovery. Invalid Web Push subscriptions are pruned on HTTP 404/410. Local auto-generated VAPID keys are intentionally temporary and must be replaced by stable production keys. Headless Chromium confirmed notification permission and an active worker but could not register with its remote push service (`Registration failed - permission denied`), so an interactive controlled-device push receipt remains open.

New-order interaction: the frontend independently queries `GET /merchant/orders?status=SENT_TO_MERCHANT`, listens for order events, and keeps an action alert visible until Accept, Reject or explicit Close. Accept and Reject call the existing lifecycle endpoints and verify the returned state with a detail refetch. Closing is browser-local acknowledgement only; it never changes backend order status.

Realtime evidence: a guarded local test customer completed OTP login and placed COD order `SB20260929-F46962` through `POST /orders`. The open Local QA Shop page received the merchant `order:new` event immediately: the persistent alert changed to the new order, its table row appeared, and the unread bell count increased without a reload. Polling remains recovery rather than the primary observed delivery path.

The local test database now contains explicitly marked disposable records used to verify populated response envelopes and persistence for orders, replacements, products, riders, staff, documents, finance, settlements and support. The frontend and backend production builds passed. These results apply to the local API/database only and are not deployed-production evidence.

Permission-boundary evidence: an ORDERS-only staff token could read `/merchant/orders`; inventory, finance, riders, owner-only staff management, admin, customer-order and payment paths were denied. This audit found missing INVENTORY checks on product list/catalogue reads; the checks were added and the guarded suite passed after rebuild.
