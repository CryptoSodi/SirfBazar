## Required behavior and remaining API gaps

The client transport bounds HTTP waits (15 seconds), coalesces guest-session creation and token refresh, retries a private 401 at most once after refresh, and serializes credential writes against account changes. Native credentials use secure storage; browser storage is a separate development surface. Location permission/GPS/geocode waits have their own finite deadlines. These are implementation properties, not native reliability test results.

Checkout is deliberately sequenced: guest basket and local delivery draft; deliberate authentication; merge and explicit basket review; authenticated address/selected-destination quote; explicit final review; explicit Place order; saved-order receipt or durable uncertain-result recovery. A transient merge failure retains the guest context. A transient placement failure retains the original request ID, cart ID, and payload. Neither sign-in, a restored draft, nor a status check is allowed to auto-place another order. Price/stock changes demand review without silently reducing quantity.

The following gates remain open:

- Real Google sign-in, SMS delivery/verification, native push registration/delivery/open, secure-storage relaunch, and background/reconnect behavior require a configured native build, device, and approved test account.
- Online payment is unavailable. COD is the supported checkout choice; pending payment recovery reads status only. Provider configuration, authorization, confirmation, failures, refunds, and settlement are not certified.
- Product-list restriction flags are incomplete. The client now fetches detail before Add/increase and blocks restricted/prescription/unknown eligibility, but this is not a security boundary. Server cart/order checks do not enforce these policy flags, so existing or externally populated restricted basket contents can bypass the Add controls. Authoritative enforcement is a release blocker, not a completed client guarantee.
- The placement DTO has no accepted quote/version or expected-total contract. The client rechecks and requires acknowledgment of observed price/stock changes, but the server recomputes live prices during placement. A change between the final GET and POST can therefore remain unacknowledged. An atomic server-validated quote contract is a release blocker for guaranteed reviewed totals.
- Guest remote clear-location and guest remove-coupon endpoints are absent. Local browse-area clearing does not promise that remote guest-session coordinates were erased. Guest coupon removal is not simulated; a different code or authenticated removal is the supported current path.
- C13 native maps, permission handling and geocoding require device verification; the browser is an explicit coordinate-entry fallback. C19/C20 do not provide a rider-location map: they disclose only a real location-report timestamp when available.
- Read/write ownership, concurrent merge/order retries, uncertain-add reconciliation, stock/price races, and native process-death recovery need approved end-to-end evidence. Current transactional server implementation must not be confused with a completed production safety test.

## Final local verification

On 2026-10-06, all 44 customer flow, checkout draft, reference-token/appearance, and purchase-safety tests passed. `tsc --noEmit` and the scoped `git diff --check` passed. The final Android and iOS Hermes JavaScript/assets exports passed after source changes, with 28 asset files and metadata; these are neither APK/IPA builds nor installed-device tests.

The in-memory fixture on port 3198 confirmed public browsing/basket, delivery draft, invalid/valid fixture OTP, failed-merge retention across browser reload, explicit merge/final review, changed-price acknowledgment, appearance/draft persistence, and uncertain-order recovery. The lost-response run recorded two HTTP placement attempts and one saved order under the same request ID. Reload/status recovery did not increase either count. A read-only transport audit found no application-level status-0 retry; the cause of the second HTTP attempt was not established. These checks do not certify the live server's concurrency or provider behavior.

All live/native evidence cells above remain unverified until their own tests are performed. See [design-deviations.md](design-deviations.md) for release limitations and [visual-parity-report.md](visual-parity-report.md) for exact evidence scope.
