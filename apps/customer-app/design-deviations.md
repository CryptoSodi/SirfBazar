## Release blockers beyond visual parity

1. **Authoritative product restrictions.** Client Add/increase checks product detail and fails closed for restricted, prescription or unknown flags. Existing/externally populated basket contents can still bypass that control because current server cart/order validation does not enforce these policy flags. Backend enforcement is required before claiming restricted-product checkout safety.
2. **Atomic reviewed totals.** The client re-reads the quote and requires review of observed changes. The server placement DTO has no accepted quote/version or expected-total contract and recalculates current prices. A change between the last quote GET and placement POST can still be accepted without acknowledgment. Idempotent request IDs prevent duplicate logical orders; they do not solve this price race.
3. **Native acceptance.** No installed Android/iOS, 84 native scene/theme captures, native accessibility approval, secure-storage process-death test, real SMS/Google or remote push pass is available. Successful Hermes exports are only a build-stage check, not release readiness.

Backend fixes were not mixed into this customer-app design implementation. No migrations, production orders, ticket publications, cancellations, account deletion, real notification writes or deployments were performed. Evidence and exact remaining test boundaries are in [visual-parity-report.md](visual-parity-report.md) and [api-status.md](api-status.md).
