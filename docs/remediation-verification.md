# Remediation verification gates

Run from a clean Node 22 checkout. Install each of the eight `apps/*` packages with `npm ci`; generate the API Prisma client in that copy. The default `rtk node scripts/verify-remediation.mjs` executes API typecheck/build/POS and mock WAHA/WhatsApp tests, web/admin/shop/POS builds, web/POS recovery tests, shop workflow tests, and customer/merchant/rider native typechecks and Node tests. It reports database, browser, native device and staging gates separately. A missing script or dependency fails the requested check.

The disposable database gate is `rtk node scripts/verify-remediation.mjs --database` with `REMEDIATION_DATABASE_URL` pointing to a unique local PostgreSQL database whose name includes `remediation_test`, on a port other than 5432/5433. The runner verifies the connected database name before running the API remediation suite. CI creates only `sirfbazar_remediation_test` on port 15437 and applies `apps/api/prisma/remediation-disposable-fixture.sql` with `psql -v ON_ERROR_STOP=1`; it does not use Prisma `db push`. Never point this mode at production or the live local database.

The browser gate uses three locally served, isolated client builds and a cached/installed Playwright module: set `BROWSER_WEB_URL`, `BROWSER_POS_URL`, `BROWSER_SHOP_URL`, `PLAYWRIGHT_MODULE_PATH`, and optionally `PLAYWRIGHT_BROWSER_EXECUTABLE`, then run `rtk node scripts/verify-remediation.mjs --browser`. All URLs must be localhost. Build the merchant client with `VITE_API_URL=http://127.0.0.1:3001/api`; build the customer web fixture without a Google Maps key to exercise the key-free picker. Every browser API request is intercepted with fixture data. The journeys verify first-address coordinate selection and quote, GET-404 versus definitive quote-rejection recovery, keyboard map selection and focus restoration, POS Charge and definite-versus-unknown saved-sale recovery, merchant category selection with partial upload retry, CSV mapping/preview/confirmation, Profile map overlay and toast behavior, dummy merchant signup OTP visibility, sign-in error and recovery request, plus iPOS toast visibility in normal, dialog, native fullscreen and fallback fullscreen modes. The browser checks create no live orders, registrations or recovery messages; screenshots are saved under `output/playwright/`. The Google-key picker requires separate configured-key verification.

The native gate runs on an Android emulator or device with separate remediation builds installed: `pk.sirfbazar.customer.remediation`, `pk.sirfbazar.merchant.remediation`, and `pk.sirfbazar.rider.remediation`. Each app's `app.config.js` selects the `.remediation` package only when `REMEDIATION_TEST_BUILD=1` and `EXPO_PUBLIC_API_URL` names a nonproduction API. Build the three apps with those two variables set and install those APKs on the test device. Set `NATIVE_DEVICE_ID`, `NATIVE_TEST_API_URL` to that build URL, and `NATIVE_<CUSTOMER|MERCHANT|RIDER>_TEST_APP_ID` to the corresponding suffix ID. For each app set `_START_TEXT`, `_TAP_TEXT`, and `_DESTINATION_TEXT` to the visible accessibility text in the prepared fixture state. `rtk node scripts/verify-remediation.mjs --native` checks installation, launches each separate test package, finds the start control, taps the named navigation control, and verifies the destination. Test accounts and any order needed to expose the chosen rider screen must be prepared on the dedicated API. The script validates the expected package identity and navigation but cannot inspect the compiled API URL inside an APK; the build configuration and test backend logs supply that evidence. This gate does not by itself prove background GPS, push delivery, or a complete order.

The staging gate requires a nonproduction HTTPS hostname containing `staging`, `test`, or `preview`, provided as `REMEDIATION_STAGING_URL` including its `/api` base. Provide fixture bearer tokens in `REMEDIATION_STAGING_FIXTURE_TOKEN` (customer), `REMEDIATION_STAGING_MERCHANT_TOKEN`, `REMEDIATION_STAGING_RIDER_TOKEN`, and `REMEDIATION_STAGING_ADMIN_TOKEN`, plus a nonempty eligible customer cart ID and owned delivery address ID in `REMEDIATION_STAGING_CART_ID` and `REMEDIATION_STAGING_ADDRESS_ID`. `rtk node scripts/verify-remediation.mjs --staging` checks public/catalogue and authenticated role reads, creates an approved COD quote, verifies missing/tampered approvals return 409, and verifies neither creates an order. It never sends an approved purchase. Full purchase, merchant fulfillment, rider delivery, refunds and settlement need a separately authorized disposable staging fixture journey.

The manual `Remediation release gates` GitHub workflow exposes native and staging as separate jobs. Native requires a self-hosted runner labeled `android-remediation` with adb and installed test builds; staging uses repository variables and secrets named above. An unavailable runner, device, secret, fixture or browser remains an unverified release gate, not a pass. Neither workflow deploys anything.
