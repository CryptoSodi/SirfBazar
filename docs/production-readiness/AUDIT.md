## Prioritized Findings

### F01 / P0: Public Registration Can Replace Existing Credentials
- Control/status: SEC-02 **PARTIAL**, confirmed authentication-bypass path in R and L; high source confidence. Live exploitability/data existence not tested.
- Routes/apps: public `POST /api/auth/merchant-register/start`, then merchant/admin password sign-in; API, shop signup, staff/admin accounts.
- Evidence: [apps/api/src/auth/auth.controller.ts](<C:/Users/tassa/.codex/worktrees/api-icons-release/SirfBazar/apps/api/src/auth/auth.controller.ts:42>); [apps/api/src/auth/auth.service.ts](<C:/Users/tassa/.codex/worktrees/api-icons-release/SirfBazar/apps/api/src/auth/auth.service.ts:295>) updates an existing user's name/CNIC/password/contact at lines 315-317 before creating or verifying OTP. It blocks an existing merchant owner, but not other accounts without a linked merchant. [apps/api/src/merchant/merchant-people.service.ts](<C:/Users/tassa/.codex/worktrees/api-icons-release/SirfBazar/apps/api/src/merchant/merchant-people.service.ts:207>) creates active staff users without CNIC/password; [apps/api/src/auth/auth.service.ts](<C:/Users/tassa/.codex/worktrees/api-icons-release/SirfBazar/apps/api/src/auth/auth.service.ts:285>) permits password login for active staff without requiring registration OTP.
- Observed invariant failure: an existing staff identity with null CNIC and a matching normalized contact can receive an attacker-chosen password through the public start step. No proof of control of that contact is required before the update. Other existing identities may also have credentials/contact changed subject to the lookup/CNIC conditions. No attack or account enumeration was performed.
- Smallest change: reject unauthenticated registration writes to every existing identity; direct legitimate existing users through authenticated onboarding/recovery. Keep the new-account OTP sequence and WhatsApp integration. Stage broader unverified-account reservation/retry design separately.
- Tests/compatibility/rollback: first batch B1 below; no schema, token, UI or provider change. Existing-identity signup gets a safe rejection instead of overwriting credentials. A revert would reopen the bypass: do not use it as an unattended rollback.
- Dependencies/approval: owner approves B1 on R; synthetic identity fixtures only. Historical account review/reset is a separately authorized operation; neither data repair nor deployment is approved.
