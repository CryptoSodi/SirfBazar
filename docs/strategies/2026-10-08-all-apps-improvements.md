## Release sequence and constraints

1. Reconcile the pending human strategy gate with this audit. The latest request authorizes publishing and supersedes the older no-push restriction; it does not select an authentication design or waive review and verification gates.
2. Establish meaningful baseline fixtures, then deliver A/B and C with disposable PostgreSQL and client regressions. Coordinate shared auth files before D/F edits. D/E may progress independently once their strategy/design dependencies are resolved; original numbering stays unchanged.
3. Release compatible web/API changes only after clean installs/builds, tenant-negative checks, browser journeys, deployment-target identification and rollback readiness. Preserve production environment, credentials and business data. Do not use live orders as tests.
4. Release G independently. A web/API deployment does not update installed mobile applications: native fixes require rebuilt, verified binaries and distribution; report installed-version coverage separately.

No schema changes, provider replacement, new payment tender, ledger/returns subsystem, background GPS, production map/billing changes or historical-data repair belongs in these packages. Retain local API `http://localhost:3001/api`; explicitly isolate native tests from production defaults. Existing Google/WhatsApp flows, tenant boundaries, signed checkout, cash/COD and durable recoveries are mandatory regressions.

Success means every original request and health finding has an owner, executed acceptance evidence and separate local/merged/live/device status. Missing device or staging evidence remains unverified. No interface approval is issued by this PM document; implementation must use the repository's interface workflow and rendered review.
