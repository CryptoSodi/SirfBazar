# Remediation and merchant workflow acceptance criteria

7 October 2026 · ATeam run `20261007T122811Z` · Strategy stage

## Problem and proposal

Customers need one reliable order per purchase; merchants need trustworthy stock, money and fast catalogue setup; riders and staff must see only authorized information. Complete all seven [remediation packages](../remediation-work-packages.md), plus category/subcategory bulk selection, existing iPOS product CSV import, visible signup OTP entry and routine iPOS success toasts. This is an implementation contract, not a new audit or product expansion.

The [research report](../research/2026-10-07-remediation-merchant-workflows.md) supplies the source gap map and official export evidence. Current code and executed checks take precedence over older architecture, API, backend, deployment, remaining-work and capability records. Stock decrement and merchant iPOS recovery already exist, WhatsApp OTP uses WAHA, and Next is already 16.4.0.

## Must-have requirements and acceptance criteria

| Package / priority | Required outcome and acceptance evidence |
| --- | --- |
| **1. Payment authority and money races — P0** | Production customers cannot confirm/fail payments or obtain paid status through mock paths. Keep cash/COD; unsupported digital tenders fail closed on the server and are unavailable in clients. Concurrent refunds credit once and cannot exceed refundable value across parent/child orders. Competing settlement generation claims each eligible order once and calculates only from claimed orders; mark-paid/hold and refund/cancellation races preserve consistent status, balances and audit. Payment state and order effects cannot partially commit. Notifications occur after commit and their failure cannot report a committed operation as failed. Verify concurrent requests on disposable PostgreSQL; process-local locks alone are insufficient. |
| **2. OTP, account state and tenancy — P0** | Suspended/deleted/inactive accounts lose protected access with existing tokens. Check active staff membership and permissions. Delivery OTP never leaks through rider/merchant lists, details, parent/child projections or mutation responses; only the authorized customer can reveal it in the permitted state. Support/order access rejects cross-customer, cross-merchant and unassigned-rider requests. Negative role/tenant tests cover affected paths; preserve valid owner workflows, anonymous browsing, WAHA delivery and OTP expiry/retry rules. |
| **3. Atomic inventory and approved checkout — P0** | Transitions, replacement stock changes and restoration commit atomically against expected prior state. Last-unit competition permits one reservation; competing cancellation/rejection/failure restores once; failed replacement leaves original stock consistent. At submission validate current merchant/product eligibility and destination, binding the order to approved items, address, prices, fees, coupon and total. Changed quotes require review before purchase. Test concurrent transitions and tampered/stale quotes; document the contract for every consuming client. |
| **4. Recovery and keyboard access — P1** | Customer web checkout and standalone POS persist request identity and immutable submission before sending. Lost responses, reload, expired authentication and retry recover by the same identity without duplicate orders or stock effects. Storage failure is explicit before unsafe submission; uncertain results remain visible until reconciled. Retain merchant iPOS recovery. Revalidate and repair both keyboard defects in the package, recording exact controls and completed keyboard paths; cover new picker/import/OTP/dialog interactions too. |
| **5. Dependencies and clean builds — P1** | Check current official advisories against every resolved Next/Multer version, including transitive copies. Apply compatible fixes and fresh lockfile installs under Node 22; do not downgrade Next 16.4.0 following stale findings. Report resolved versions and clean builds. Malformed/aborted upload regression checks terminate safely and preserve upload limits. |
| **6. Eight-app verification — P1** | CI covers API, customer web, admin, merchant web, standalone POS, customer mobile, merchant mobile and rider mobile. Browser/API builds and native typechecks/tests are explicit. Add disposable-database concurrency/auth regressions and browser journeys for OTP, recovery, bulk selection/import and normal/native/fallback fullscreen toasts. Provide native/emulator and staging journey checks with explicit prerequisites; unavailable infrastructure is not run, and web tests never count as native execution. |
| **7. Search, push, GPS and claims — P1** | Search displays only the latest query/location result, including delayed location resolution. Push registration belongs to the current session; logout/account switch cannot attach stale tokens to another account, with server ownership cleanup verified. The active rider delivery screen sends foreground location only for an authorized active delivery, handles denied permission and stops on delivery end/logout. Test lifecycle races and correct capability documentation. Background GPS is excluded. |

## Merchant workflows — P1, required in this delivery

**Bulk selection.** Choose a responsive full-page three-pane layout: category/subcategory navigation, selectable product grid, selected-items price/stock editor. It matches the supplied reference and keeps review visible. A narrow drawer compresses bulk editing and obscures the grid; reserve it for sequential import. On narrow screens stack/disclose regions in reading order, keeping selected count and review reachable.

Selection survives category/search/pagination changes. Select-all explicitly applies to visible eligible products; already-listed items are marked and excluded. Review price and whole-unit stock before adding; reject invalid values and prevent duplicate submission. Partial failures retain failed rows and edits; successes are accounted for. Cover collapsed/expanded categories; loading/error/retry/empty grid; selected/unselected/already-listed products; empty review; invalid values; submitting; partial/full success. Reuse existing hierarchy and moderation.

**Existing iPOS import.** Add CSV file selection with paste fallback and a drawer sequence: file → editable header mapping → preview → confirmed import → row results. Official evidence establishes CSV export without verified headers: support unfamiliar external headers, never claim an official iPOS schema. Match catalogue identity unambiguously and preserve SKU/barcode strings, including leading zeros. Parse quoted commas, escaped quotes, embedded newlines, BOM and common line endings; reject malformed/oversized files with recovery instructions.

Preview required fields, matched/new/skipped/conflicting rows, price in rupees and stock units. Distinguish sale price from cost and quantity from stock value. Reject duplicate/ambiguous identities, nonfinite/negative values, unsafe paisa conversion and fractional packaged stock. Missing stock needs an explicit value or suitable report; never silently assign zero. Default to **add missing only**. Existing price/stock updates require explicit update mode and confirmation showing changed values. New catalogue items follow moderation. Show row errors and counts; retry must not reapply successful changes. Excel users can save as CSV. Generic XLSX is optional only with safe sheet/header selection; it is not verified iPOS compatibility.

**Signup OTP.** The six-digit input has a visible label, surface/border and readable text in empty, focused, filled, invalid and disabled/submitting states. Preserve paste, one-time-code autocomplete, validation, resend and the OTP provider.

**iPOS feedback.** Routine add/hold/save success uses existing toasts, politely announced without shifting scanner focus or page layout. Verify visibility in native/fallback fullscreen and around dialogs. Uncertain sales, persistence failures, actionable errors and capability restrictions stay persistent with a clear recovery action.

## Constraints and completion gate

- No Prisma schema or `app.module.ts` changes, API restart, production database mutation/tests or deployment. Keep local API configuration at `http://localhost:3001/api`. Preserve working features and existing components/tokens.
- All seven packages and four merchant outcomes are mandatory. Nice-to-have: generic XLSX and mapping presets. Out of scope: provider adapters, new financial ledger, background tracking, taxonomy redesign and unrelated features.
- Interface skills inform native semantics, focus restoration, labels/errors, semantic colors and responsive layout. Before interface approval inspect keyboard/screen-reader paths, 320px reflow, 200% zoom, long names/barcodes, rendered contrast and reduced motion. This strategy is not visual approval.
- Completion requires requirement-to-evidence reporting: behavior, executed command/journey, outcome and limitations. Available relevant checks must pass; blocked staging/native infrastructure remains an explicit unverified release gate. Strategy has no executable verification command; implementation/QA must create and execute the agreed remediation verification runner.

No product choice blocks implementation under these defaults. Architect must define schema-preserving transaction and quote/recovery contracts. Missing staging/emulator resources affect verification claims, not authorization to complete available work.
