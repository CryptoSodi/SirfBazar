Backend source is frozen for client integration. `GET /auth/me` includes `rider.approvalStatus`; pending/inactive RIDER sessions may call only `/auth/me` and `/rider/profile`. Operational rider routes require approved, active membership. Address delivery-field edits and deletion used by an active order return HTTP 409 `{code:"ADDRESS_IN_USE",message}`. Admin cancellation returns `{ok,status,returnReviewRequired,returnReview}`; confirmed goods already picked up are held for physical-return review. Admin repair accepts only `SENT_TO_MERCHANT→MERCHANT_ACCEPTED`, `MERCHANT_ACCEPTED→PREPARING|READY_FOR_PICKUP`, or `PREPARING→READY_FOR_PICKUP`, with a 3–500 character reason and domain prerequisites.

New notifications persist `type = v1:<CUSTOMER|MERCHANT|RIDER|ADMIN|ACCOUNT>:<scopeId>:<baseType>`. HTTP/socket responses restore the base `type` and add `audience,scopeId`. Default `GET /notifications` remains an array of eligible current rows; `?scope=legacy` returns pre-versioned rows separately. The same scope query applies to `POST /notifications/:id/read` and `/notifications/read-all`; invalid values are rejected. Clients must expose “Earlier account notifications” separately and exclude it from current badges. This implementation conservatively classifies all pre-versioned rows as legacy; the approved design's unambiguous-history inference remains unimplemented. Push payloads add `audience,scopeId`.
